# Partial implementation

Classify each changed area as complete-and-proven, implemented-but-unverified, partial, broken, or unrelated. For each area record owner, changed contract, current consumer state, first failing proof, and next dependency. Verify interfaces before continuing and protect unrelated dirty files. Prefer finishing the smallest coherent slice over opening new fronts; never hide a broken producer behind consumer guards.

## Reconcile the proof chain

Reconcile source, task and proof state before resuming: locate canonical ticket/spec/plan or chat brief, existing requirement/decision/task/test IDs and revisions, acceptance, implementation diff, test expectations, Consumes/Produces and actual receipts. Preserve stable IDs, approved decisions, unrelated work and historical proof. Reopen decisions only for an evidenced conflict; keep the existing whole-Brief approval boundary.

Reject stale completion claims as `implemented-unverified`. Inspect requirement/spec changes, implementation changes after receipt, changed test expectations, producer-contract changes and blocking review gaps; revalidate affected proof and known dependents before claiming completion. Preserve unrelated applicable proof only when diff/dependency evidence shows the verified invariant and its execution context are unchanged. Unknown provenance or uncertain impact remains unqualified; a checkbox, old PASS, document hash or agent assertion supplies no fresh verification. Missing/unexecuted checks remain `NOT_RUN`; failed/blocked evidence keeps its actual outcome. Resume Test when only proof is missing rather than redo proven implementation.

A deferred task becoming dependency-ready is not complete. Revisit the deferral reason, current scope/approval, dependencies and revisit condition; consult the owner if known when the recorded disposition does not settle scheduling. If the trigger is met and scope is already authorized, use the existing Git/Build checks with no new approval. Unmet in-scope acceptance still blocks completion. Receiving producer proof only enables the next dependency-ready action; it supplies no consumer proof or mutation authority. Return task dispositions, scoped applicability/revalidation reasons, exact observed receipts, independent review verdicts, unresolved blockers and the next safe owner/action in the existing ledger/chat handoff.
